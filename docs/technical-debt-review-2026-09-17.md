## TD-01：会话锁与业务查询共享有限连接池

位置：`apps/api/src/memory/memory.service.ts:17`、`:158`，`apps/api/src/agent/agent.service.ts:79`。

连接池上限 12。`acquireSession()` 持有一个数据库连接和 session advisory lock，直到模型整轮执行结束；接着 `archive()`、概要加载和记忆工具又通过同一个 pool 申请连接。后台整理也会长期占用一个连接。HTTP 不受 WebSocket 的 8 连接上限约束。

当足够多的不同会话同时持锁，后续业务查询可能全部等待空闲连接，并在 5 秒取连接超时后失败。这是可触发的连接池饥饿，不应描述为永远不释放的数据库死锁，也不能单纯调大 pool 当作根治。

建议：先加有限的运行准入并预留业务查询容量；将锁连接与短查询池隔离，或设计可续期、带所有权校验的会话租约。明确锁连接断开后的取消与写入保护。锁释放失败时也必须销毁/释放客户端，避免 `await unlock` 抛错跳过 `release()`。

验收：独立数据库中让并发运行数超过准入上限；超额请求快速返回可重试状态；已接纳请求仍可归档和检索；模型慢响应、数据库连接中断、取消均不泄漏连接。

2026-09-17 修复记录：

- 在临时 PostgreSQL 17 上复现原实现：后台占用 1 个连接，12 个并发会话请求后，`archive()` 因等待连接而超时。
- 保持池上限 12，新增每进程最多 8 个 SDK 会话的同步准入，为单个后台 worker 和短查询留出容量；超额返回 503，不调用模型或写入原文。
- 名额覆盖初始化、运行和快照保存全过程；保存/释放函数幂等，初始化与保存失败均归还名额。解锁失败销毁连接，避免带锁连接回池；SDK dispose 抛错也会释放数据库会话。后台 worker 的解锁失败同样销毁连接。
- 新增 `apps/api/test/memory-capacity.test.mjs`：真实数据库满载下的归档/检索、超额拒绝、快照恢复，以及 Agent 成功/取消/模型失败后的容量复用；用故障注入覆盖连接申请、归属检查、文件恢复、快照保存、解锁和 SDK 清理失败。
- Node 24 下针对性测试 12 项通过、零跳过。实际数据库断连导致的锁所有权丢失与跨实例接管尚未做故障演练；本次验证不代表完成该类容灾验证，也未做生产压测或部署。
- 修复后 `pnpm typecheck` 通过；使用临时 PostgreSQL 显式设置账号与记忆测试库，完整 `pnpm test` 共 151 项通过、零失败、零跳过。原审查的 123/3 记录是修复前基线，保留供对照。数据库验证已在本次执行，但 TD-05 所要求的自动发布门槛仍待实现。

## TD-02：后台候选筛选会造成跨用户饥饿

位置：`apps/api/src/memory/memory-worker.ts:51`–`:61`。

候选 SQL 按 pending/running 任务挑最早的 20 个用户；进入循环后才检查该用户最早的未完成任务是否 failed。若 20 个用户都有“前序 failed + 后序 pending”，这些用户会反复占满候选窗口，并全部被跳过，其他用户始终选不到。

同用户 failed 阻止后续任务越序是合理约束，问题是它扩散到了其他用户。应先找每个用户真正的队首任务，再筛选可执行状态和到期时间，最后排序、限额。失败任务需有可见告警和恢复入口。

验收：构造 20 个被失败队首阻塞的用户和第 21 个正常用户，确认后者能被领取，且前 20 个用户不能越序。另做持续积压测试；当前一个进程全局串行整理，后续如需并发，应保留同用户串行并限制总并发。

## TD-03：删除附件会破坏 Gemini 历史会话

位置：`apps/api/src/agent/pi-session.factory.ts:47`–`:54`，`apps/api/src/materials/gemini-files.ts:13`–`:15`。

每次创建 Gemini 会话都会重新准备 workspace 中全部历史资料，包括当前未展示的资料。删除原件后，历史附件快照仍然存在；`GeminiFiles.get()` 查资料时返回 404，导致整个会话在模型启动前失败，连普通闲聊或切回对话都无法执行。

最小复现：上传合成 TXT → 登记到 workspace → 切到 conversation → 删除资料 → 不传新附件重新创建 Gemini 会话。实际得到“资料不存在”404；通过 Agent 入口会被包装成运行失败。没有调用外部模型。

建议：区分历史附件快照和当前可用原件。删除后用明确的失效标记保留历史，不再注入失效的 native file；用户显式要求读已删除原件时再返回清楚错误。不得通过绕过归属校验解决。顺便避免每轮把所有历史附件重新注入模型导致上下文持续膨胀。

验收：删除非当前附件、删除当前附件、旧 Google 文件过期、切换 provider 后，普通对话仍可进行；不能读取被删除或越权的原件。

## TD-04：初始化期间的超时只有标记，没有取消底层工作

位置：`apps/api/src/agent/agent.service.ts:71`–`:86`，`apps/api/src/materials/gemini-files.ts:38` 起。

定时器仅调用 `session?.abort()`；等待 `factory.create()` 时 session 尚不存在，底层资料转换、文件上传、状态轮询也没有接收整轮 AbortSignal。多附件逐个准备时，每份各自的超时可能累计远超 AGENT_TIMEOUT_MS。用户挂断也仍可能继续上传并占着会话锁。

最小复现：AGENT_TIMEOUT_MS=20ms，模拟 factory.create 延迟 180ms；实际约 182ms 才返回 408。

建议：整轮统一 deadline 和 AbortSignal，传入 factory、文件准备、fetch、转换子进程及数据库等待；取消后等待资源清理再释放会话所有权。不能只加 Promise.race，让后台工作继续改文件。

验收：初始化、上传、轮询、生成和最终保存各阶段分别取消；确认不继续发起下一步骤，资源和锁在约定时间内释放，没有迟到写入。

## TD-06：高成本请求缺少系统性的容量边界

位置：`apps/api/src/voice/voice.gateway.ts:35`，`apps/api/src/agent/agent.service.ts:32`，`apps/api/src/materials/materials.controller.ts:19`，`materials.service.ts:159` 起。

已有短信限流、文件 20 MB 上限、语音帧/时长限制以及全局 8 个 WebSocket 限制，这些应保留。但 HTTP 可通过新 conversationId 绕过单会话互斥；上传整文件进内存并在 API 进程完成解析，PDF 全量抽取后才截正文；页预览也重复加载/渲染。语音全局名额没有按用户公平分配。

在 1 GiB API 容器中，多份合法大小的复杂文件并发也可能耗尽内存；一个账号可以占满语音名额或制造大量模型请求。这是容量/费用暴露风险，本轮未做压测，不能提供安全并发数。

建议：用户级及全局并发准入、调用预算、有限队列与清楚的繁忙响应；解析/转换用受限工作进程，限制页数、解析时间和解压规模，缓存页预览。先测容量，不直接引入分布式队列。

验收：恶意突发和正常混合负载下内存有上限，单用户不能挤占全部容量，拒绝的请求不会继续调用收费服务。

## TD-07：业务作品依附 SDK 快照，资料索引依赖本机

位置：`apps/api/src/memory/memory.service.ts:169`–`:190`，`apps/api/src/agent/agent.service.ts:143`，`apps/api/src/materials/materials.service.ts:34`–`:44`。

作品与 persona、session.jsonl 一起在整轮结束时写回数据库；实时 panel 更新先发给客户端，进程中途崩溃时，下次恢复数据库旧快照会覆盖本地文件。因此“屏幕已更新”和“可跨崩溃恢复”不是同一时点。

OSS 已保存原件，但 metadata.json、storage 标记和转换缓存仍在本机。仅恢复数据库和 OSS、迁到无文件卷实例，资料列表依然不可用。文稿列表还会读取所有会话的完整 panel JSON 再提取标题，缺少分页。

建议分两步：先明确客户端保存状态，补故障恢复验证；再把作品及版本、资料元数据变成独立业务表，以数据库作为索引真相，OSS 保存对象，SDK 快照只负责对话恢复。采用可重试的上传/删除状态处理跨存储失败。迁移期间保持单实例约束。

验收：工具改稿后强制终止进程，已确认保存的版本不能消失；从数据库与对象存储恢复到空目录仍可列出资料与作品；列表有分页，不全量解析正文。

## TD-08：Trace 位于实时关键路径且无限增长

位置：`apps/api/src/agent/agent-storage.ts:30`–`:35`，`apps/api/src/agent/agent.service.ts:89`–`:93`。

每个模型文本增量同时产生 Pi 和产品 Trace，同步 appendFileSync 会阻塞整个 Node 事件循环。磁盘变慢影响所有语音连接；写盘失败还会终止 Agent。未见 Trace 文件的轮转/过期清理，Docker 日志轮转不会清理这些 JSONL。

建议：有序、有限缓冲的异步写入，区分可丢弃的调试增量与必须持久化的业务证据；设置 Trace 大小/保留周期、敏感正文记录策略、磁盘告警。避免无界内存队列。

验收：模拟慢盘、磁盘满和长会话，业务证据保持既定可靠性，语音延迟不会因每个 trace 增量同步阻塞；到期记录按策略清理。

## TD-09：探活和备份无法证明服务可用、数据可恢复

位置：`apps/api/src/health/health.controller.ts:7`，`infra/production/compose.yml:23`，`infra/production/backup.sh:9`。

health 无条件返回 ok，仅用 pool 是否存在表示 memory enabled，数据库已断开时仍可能健康。备份是同机 14 天的 pg_dump + 在线 tar；主机丢失会同时失去主数据和备份，数据库/文件也不是同一时点。部署文档已说明这些局限，不应误认为已有容灾。

建议：区分 liveness 与 readiness；readiness 用有超时的数据库检查与必要存储条件，不把每次外部模型探活绑进去。记录记忆失败/积压、连接池等待、语音失败阶段等指标。增加异机备份和定期恢复演练，明确可接受的 RPO/RTO。

验收：数据库失联时 readiness 失败而 liveness 可保留；从备份恢复到空环境后验证账号、作品、资料、原文和引用；记录实际恢复时间与可丢失窗口。

## TD-10：身份入口和持久化职责应逐步收口

位置：`apps/api/src/memory/memory.service.ts:26`，`apps/api/src/memory/memory.controller.ts:11`，`apps/api/src/memory/memory-worker.ts:50`。

多个 controller 依赖可选 MemoryService 来解析身份；MemoryService 同时负责身份兼容、用户、会话锁、SDK 快照、通话、消息、检索和事务提交，controller/worker 还直接访问 public pool。当前没有因此确认权限绕过，但新路由容易遗漏手工身份调用，存储变更也会波及无关职责。

建议：建立统一 HTTP Guard/用户上下文及 WebSocket 身份适配；显式区分 production account 与 local preview 模式；按现有职责抽出 session、call、memory、job repository。认证不再由记忆模块承担。启动 DDL 后续改成可记录版本的迁移，并验证前后版本兼容；不为简单查询增加通用 repository 框架。

验收：全部受保护路由跑无身份/本人/他人矩阵；禁用记忆不改变生产认证边界；controller 不再直接写任务表。

## TD-11：前端入口需要按状态所有权拆分

位置：`apps/debug-console/src/App.tsx:89` 起（当前约 1043 行）。

入口同时承载文字运行、语音、麦克风、播放、字幕、资料选择、回执、历史、模型选择和调试 UI；分散的 state/ref 让关闭、取消、账号切换、迟到回调等边界难以整体推理。此项是可维护性债，不凭文件行数宣称已有竞态 bug。

建议先提取 useCallSession、useAgentRun 和 workspace 状态，再隔离调试面板。用明确状态转移管理互斥状态，保留运行/连接标识过滤迟到事件。两端只共享纯协议与状态归约，不强行共用浏览器和微信音频实现。

验收：挂断、切后台、断网、账号切换、旧事件迟到后，麦克风/音频正确释放，旧结果不覆盖新会话；拆分不改变现有视觉和交互。
