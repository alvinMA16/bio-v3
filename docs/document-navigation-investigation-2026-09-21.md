# 文稿定位与高亮排查（2026-09-21）

## 线上证据与结论边界

用户在 `/internal/` 测试。线上该路径与根路径由同一 index.html 提供，调查时均引用 `main-Dp7IYcTd.js`；这只能确认服务器发布内容，不能证明用户原有标签页已经刷新。

15:09 的定位与 15:10 的标题高亮请求均指向正确的 b9 标题块，服务端也发出了 focus / highlight 面板事件。两次工具都在约 2 秒后得到 unconfirmed、rendered=false，原因是没有有效匹配回执。15:10 模型仍宣称已标出，和工具结果不一致。

现有历史 Trace 不包含浏览器接收、阅读器开始执行或每次 document.view 入站记录，因此无法事后确定原始故障点。本地实际 App 链路未复现相同的滚动失败，不将旧页面缓存、滚动容器或回执丢失中的任何一个认定为已证实根因。

## 本次改动

- WebSocket 收到定位面板立即回 received 与实际脚本文件名；阅读器启动回 rendering；完成回 visible/failed。所有阶段使用同一 requestId。
- 最终回执带纵向目标/视口坐标、滚动前后位置、尝试次数和前端耗时；目标高亮独立检查。视口需与浏览器实际视口相交，缺失滚动容器立即明确失败。
- 后端只对终态结束等待；超时保留最后阶段。Trace 保存 document.view 入站元数据及轮次接受结果，无正文。未匹配回执仍不等于已定位根因。
- Pi 0.84.4 将正常返回的工具统一标为 isError=false；普通返回值中自行增加 isError 也不生效。因此定位未确认或失败时抛出包含结构化结果的错误，确保 SDK、模型和前端收到真实失败标志；已有展示状态不回滚。
- 前端标记说明不再在确认前宣称“已标出”。这改善失败信号，不能保证生成模型绝不误述。
