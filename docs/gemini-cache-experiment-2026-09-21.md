# Gemini KV Cache 实验与后续讨论交接

日期：2026-09-21。实验基线：`4faedf77abae62b8edfcb83e53b02576a1393cb8`。

**结论：Google API 和 Pi 流式适配器都能记录有效缓存命中。动态状态后置在历史会话重建实验中有小幅改善，但总体命中仍低，尚未证明是稳定、足够的优化。生产上下文排列和缓存策略未修改；用户希望在新会话继续讨论，先不要直接改缓存代码。**

## 问题与现有实现

当天 13:34–13:39（北京时间）的一通电话包含开场及四轮交流，共 8 次模型调用。SDK 记录输入合计 100,275 tokens，缓存读取为 0。模型为 `gemini-3.8-flash`，Google 官方 `generativelanguage.googleapis.com`，思考等级 LOW，开启内置 Google Search；Pi AI 版本 0.84.4。

`createContextExtension` 每次模型调用前重建 `bio_runtime_context`，插在最新用户消息之前；它包含文稿、屏幕可见范围和操作指引，工具循环中也会变化。该动态内容会截断其后的稳定消息前缀。原会话的系统提示、工具及配置指纹相同，后续调用曾保留 8 条、约 21.8 KB，以及 12 条、约 28.3 KB 的相同消息前缀，但均未记录命中。字节前缀不等于供应商实际可缓存的 token 前缀。

观测记录位于原运行 Trace 的 `model.request` / `model.response`。目前只保存请求指纹和 SDK 归一化 usage，无法区分供应商原始缓存字段缺失与显式返回零；`rawCacheFieldPresence=unavailable` 表示未采集，不能解读成确定零命中。

## 合成请求验证

实验沿用生产模型、凭据和网络，在临时脚本中发送合成资料，不修改线上配置。显式缓存 TTL 为 300 秒，读取后已主动删除。

| 实验 | 结果 |
| --- | --- |
| 约 51k tokens，完全相同请求连续 3 次 | 首次未返回缓存字段；后两次各命中 45,023 / 51,016，88.25% |
| 同样长输入，带 Google Search 工具配置，连续 2 次 | 第二次命中 48,939 / 51,016，95.93%；这验证工具配置兼容，未要求实际搜索 |
| 创建显式缓存，再读取 2 次 | 两次都命中 51,016 / 51,021，99.99% |
| 经过实际 Pi Gemini 流式适配器，重复长请求 3 次 | 每次正确记录 cacheRead=45,024；该组可能复用了此前实验已预热的内容 |
| 约 6.8k tokens，带搜索及函数工具配置，完全重复 3 次 | 后两次各命中 3,964 / 6,791，58.37% |
| 同等短输入，开头状态每次变化，3 次 | 均未返回缓存字段 |
| 同等短输入，仅末尾状态变化，3 次 | 均未返回缓存字段 |

由此可排除“API 普遍不支持缓存”及“Pi 把所有命中归零”。但隐式缓存没有必命中保证，短输入末尾变化也没有稳定命中。显式缓存测试未覆盖生产完整工具组合及缓存生命周期，不构成直接上线依据。

缓存也不保证低延迟：Pi 长请求三次都命中，耗时仍约 3.3、9.3、16.3 秒。这不是严格延迟基准，不应由此推断具体服务端瓶颈。

## 真实历史会话重建 A/B

使用这通会话保存的历史消息、真实工具结果、文稿面板及提交时视口，通过生产上下文构建函数重建 8 个请求。A 使用现有位置，B 仅把动态状态移到消息末尾。第一轮依次 A→B，第二轮 B→A，共 32 次调用。每组输入合计 87,699 tokens；返回的工具调用均未执行，未重复编辑用户文稿。

| 轮次 | 原排列缓存 tokens / 输入 tokens | 后置排列缓存 tokens / 输入 tokens |
| --- | --- | --- |
| 第一轮 | 0 / 87,699，0% | 4,242 / 87,699，4.84% |
| 第二轮 | 3,898 / 87,699，4.44% | 4,238 / 87,699，4.83% |
| 合计 | 3,898 / 175,398，2.22% | 8,480 / 175,398，4.83% |

后置组观察到约 2.61 个百分点的改善，但原排列只有 1/16 次命中，后置也只有 2/16 次，样本不足以证明稳定收益。相邻请求的相同消息前缀由原排列的 `0,2,2,2,8,8,12` 条变为后置的 `1,3,5,7,9,11,13` 条；前缀更长并未转化为普遍命中。

限制：

- 没有留存完整原始请求体、历史系统记忆摘要及所有中途视口反馈，因此是重建对照，不是逐字节原样重放。两组固定使用不含历史记忆摘要的同一系统提示。
- 两组输出上限均为 128 tokens，部分回答因此截断；实验未评估完整答案质量和完整 Agent 执行效果。
- 输入历史固定为原会话内容，不接入实验新回答，避免两组后续历史分叉。
- 同一模型与凭据共享隐式缓存，反转顺序不能消除全部预热、路由、过期等干扰，不能把差异全部归因于排列。

## 新会话建议先讨论什么

1. 明确目标：减少输入费用、降低首个可听反馈时延、还是提高跨轮复用；分别度量，不用单一命中率代替体验。
2. 在可控实验中补原始 usage 字段存在性及可重放输入，保护正文和凭据；区分缓存字段缺失与零值。
3. 扩大真实长度和工具循环样本，并验证后置动态状态不会使模型误读最新用户意图、旧工具结果或屏幕状态。
4. 比较隐式缓存优化与显式稳定前缀缓存：工具兼容性、用户隔离、TTL、更新失效、存储费用和清理策略都需要验证。
5. 用户确认方案后再实施；当前版本只处理定位回执和过渡话术，未改 KV Cache。

代码入口：`apps/api/src/agent/agent-context.ts`（上下文排列）、`pi-session.factory.ts`（扩展顺序和系统提示）、`model-observation.ts`（观测）、`apps/api/src/models/gemini-search.ts`（搜索配置）。部署参见 `infra/production/README.md`。

数值证据保存在 [逐请求实验记录](experiments/gemini-cache-2026-09-21.json)，仅含实验配置说明、用量和时延等结果，不含真实文稿正文或凭据。本地原始 Trace 和临时实验脚本未加入 Git。

新会话可直接使用：

> 请先阅读 docs/gemini-cache-experiment-2026-09-21.md 和对应实验记录，继续讨论 bio-v3 的 Gemini KV Cache 优化。API 与 Pi 已验证能命中；历史重建对照中动态状态后置从 2.22% 提升到 4.83%，但样本小且存在缓存预热干扰。先提出下一步可验证的实验与方案，不直接修改生产缓存策略。

## 第二次实验：三组缓存对照（2026-09-21 15:25–15:29，北京时间）

**结论：在本次合成样本中，显式缓存启用后的 14 次读取全部复用了指定前缀，三组总体缓存 token 比例分别为 0%、31.73%、54.65%。但没有证明显式缓存能稳定降低首段文本时延，也没有证明每次比隐式缓存覆盖更多 tokens。**

### 输入与方法

- 执行版本：`a7d5b13549da9edbec70935c729ae0e48e93a6e0`，不同于第一次实验的代码基线；模型仍为 `gemini-3.8-flash`，官方 Google API，LOW thinking，Pi 0.84.4，底层 `@google/genai` 1.52.0。
- **本次使用纯合成数据，不是上一通真实电话重放。** 原计划的真实历史重放被自动审批拦截，原因是再次发送聊天和文稿到 Google、创建远端缓存需要明确授权；已向用户询问，执行本次实验时尚未收到该授权。合成分支不读取 Trace、不加载私人记忆或真实文稿。
- 8 个递增上下文：中文虚构果园资料及简短对话；每次改变视口片段，第 5 次改变文稿版本。输入约 11.7k–11.9k tokens，第一条用户消息含约 2.5k tokens 的合成资料，不能代表短开场的全部真实通话。
- 复用生产上下文构建函数、内容工具与记忆工具定义，以及 Google Search 配置和 `includeServerSideToolInvocations=true`。通过 Pi 转换得到 SDK 请求参数，再由同版本 Google SDK 流式请求，以直接收集原始 usage。不是完整 Pi Agent 在线执行测试。
- A `original`：运行状态插在最新用户消息之前；B `tail`：状态放在历史末尾；C `explicit`：展开后的内容与 B 完全一致，但用显式缓存 ID 引用稳定前缀。每次对缓存前缀、系统提示和工具配置做一致性断言。
- 两轮，每轮三组各 8 次，共 **48 次有效生成请求**。同一 case 内轮换组别顺序，第二轮反转；历史使用固定合成回答，不接入实验新回答。每组输入均为 188,972 tokens。
- 显式组每轮第 1 次不建缓存，第 2 次缓存系统提示、工具、上一次请求的稳定历史；第 5 次删除旧缓存并扩大历史边界。动态运行状态始终不缓存。TTL 600 秒，创建 4 个缓存，全部主动删除成功。
- 输出上限为 512 tokens，提示只回复“收到”。48 次均正常 STOP，没有截断；未执行任何返回的客户端工具调用，未主动要求实际搜索。这个控制减少了输出长度差异，但不评估复杂任务质量。

### 总体结果

缓存比例按 `sum(cachedContentTokenCount) / sum(promptTokenCount)` 计算；缺失字段在合计中计 0，同时保留字段是否存在。

| 组别 | 命中请求 / 总请求 | 缓存 tokens / 输入 tokens | 缓存比例 | 首段文本中位数 | 生成耗时均值 |
| --- | --- | --- | --- | --- | --- |
| 当前排列 | 0 / 16 | 0 / 188,972 | 0% | 3.689 秒 | 4.320 秒 |
| 状态后置 | 8 / 16 | 59,958 / 188,972 | 31.73% | 3.895 秒 | 6.926 秒 |
| 显式稳定前缀 | 15 / 16 | 103,281 / 188,972 | 54.65% | 3.679 秒 | 4.541 秒 |

显式组的 16 次包含 2 次未启用显式缓存的首请求，其中 1 次获得了隐式命中。因此，不能把 15 / 16 称为显式缓存成功率。**真正引用缓存 ID 的是 14 次，14 次全部命中，累计 95,270 cached tokens，每次恰好等于对应缓存创建时的 token 数。** 这是本次样本的观察，不是对未来可用性或命中率的保证。

### 分轮结果与不稳定现象

| 轮次 | 当前排列 | 状态后置 | 显式组（含每轮首请求） |
| --- | --- | --- | --- |
| 第一轮 | 0 / 94,486，0% | 8,001 / 94,486，8.47% | 55,646 / 94,486，58.89% |
| 第二轮 | 0 / 94,486，0% | 51,957 / 94,486，54.99% | 47,635 / 94,486，50.41% |

- 后置组第二轮远高于第一轮，且第二轮比显式组的总体缓存比例还高。这与预热或服务端隐式复用行为影响结果相容，但没有服务端证据可以确定具体原因。
- 三组、两轮共享模型和凭据，显式缓存创建也可能干扰隐式缓存。轮换顺序不能消除这种影响；这些数值不应视作三个互相独立的实验总体。
- 当前排列的 16 次均缺失原始缓存字段；后置组缺失 8 次；显式组缺失 1 次。没有把字段缺失写成供应商显式返回零，也没有再仅依赖 Pi 归一化值。
- 显式缓存的两种前缀分别为 **6,769 和 6,832 tokens**（包含系统提示和工具）；单独历史内容的 countTokens 分别为 2,499 和 2,562。全量输入约 11.8k，剩余约 5k 的动态运行状态和尾部仍需输入，因此这里不应期待接近 100% 的总输入命中。
- 某些隐式命中约 8k tokens，超过显式固定前缀的约 6.8k；固定边界提高可控性，但也可能比服务端当次隐式缓存覆盖更少内容。

### 时延、准备开销与费用口径

- 表中“首段文本”是 SDK 收到首个非 thinking 文本片段的时间，不是句子完成、TTS 首包或用户听到声音的时间。“生成耗时”不包含建缓存及删除缓存。
- 三组首段文本中位数约 3.7–3.9 秒，当前排列与显式组相差仅约 10 毫秒，不足以支持提速结论。
- 后置组第二轮第 4、5 次分别耗时 18.325、30.246 秒，拉高均值；原始记录保留这些长尾，不删除异常值，也不把它们直接归因于缓存策略。
- 四次缓存准备（**countTokens 请求 + 创建缓存**）分别为 4.506、4.896、2.280、3.839 秒，总计 15.521 秒；四次删除总计 9.213 秒。第 5 次的同步刷新还要等待旧缓存删除。
- 将创建准备和所有删除时间都摊入显式组的 16 次请求，平均每次约 **6.087 秒**，高于仅生成的 4.541 秒。这是生命周期总工作量的摊销，不代表每次用户等待；轮末清理也计在其中。生产方案应评估复用更久、按增长量刷新，以及避免让同步缓存管理阻塞语音响应。
- 本次未取得该账户 `gemini-3.8-flash` 的可靠实际计费单价，因此不编造人民币/美元节省额。记录的缓存 token 比例不是费用节省比例。费用核算需分别计入未缓存输入、缓存读取、缓存创建（若该计费方案收费）、存储、输出及可能的搜索费用。四个缓存创建的总 token 数为 27,202，TTL 均为 600 秒，均提前删除；创建/删除结果与时间戳已保留。

### 本次支持的判断与下一步

1. **支持继续验证显式缓存管理。** 生产代码生成的 Google Search + 函数工具配置可与本次显式缓存请求共存；稳定前缀在 14 次引用中全部复用成功。
2. **不支持仅靠后置便能稳定命中，也不支持“命中就一定更快”。** 后置本次确有命中，但轮间差异很大；时延收益未建立。
3. 第 5 次文稿更新时，三组输入 token 数仍一致，显式组展开后的请求与后置组逐对象一致；这只验证没有因缓存拼接丢失最新运行状态，不验证模型是否正确理解状态。下一步仍需真实历史和真实工具循环、答案质量、缓存失效/过期的验证。
4. 本次按固定 case 扩大缓存只增加 63 个缓存 tokens，却发生删除与重建开销。更合理的候选策略是按可新增的稳定 token 数与预期剩余调用次数决定刷新，而不是照搬固定轮数。
5. 静态操作指引与动态视口仍混在运行状态中。可在下一次独立实验比较拆分后的缓存边界；本轮没有同时修改提示词结构，以免混淆变量。

生产上下文排列和缓存代码未修改，未部署。真实历史样本重放仍待用户明确授权。

### 实验入口错误与留档

正式实验前，独立 SDK 入口漏设 `apiVersion=''`，在已包含 `/v1beta` 的 baseUrl 上重复拼接版本，导致 48 次生成和 14 次缓存创建全部返回 HTTP 404；另有 14 次 countTokens 因 Gemini API 不支持其 config 中的 systemInstruction 而在客户端失败。无模型 usage、无创建成功的缓存。这是**实验入口配置错误，不是缓存不命中**，不计入上面的 48 次有效请求。

随后按 Pi 的 SDK 初始化方式修正 URL，countTokens 只计历史内容，完整缓存 token 数读取创建结果；并加入生成请求失败即停止的逻辑。错误尝试也独立留档，后续实验沿用“有效结果与执行失败分别记录”的方式。

- [入口配置错误记录（不纳入对照统计）](experiments/gemini-cache-2026-09-21-v2-setup-failure.json)

## 当前决策与实现：状态后置 + 显式稳定前缀（2026-09-21）

用户确认采用第二次实验的 C 组方向。**C 组本来就是“状态后置与显式缓存叠加”，不是保持原排列的显式缓存。** 当前决策优先提高稳定内容复用的可控性；不把实验中的缓存比例等同于费用节省比例，也不承诺首个可听反馈提速。

### 缓存边界

- 仅 Gemini 原生请求将 `bio_runtime_context` 放到消息末尾；其他模型保留现有排列。运行状态每次调用重新生成，包含工具执行后的最新状态，不写回持久聊天历史。
- 缓存系统提示（含该请求实际提供的记忆概要）、工具定义、Google Search 和工具配置，以及运行状态之前的一段历史。历史可含既有用户消息、模型回复、工具结果与附件引用；保留原始结构及 thought signature。
- 当前运行状态整体不进缓存，包括文稿快照、视口、模式及仍放在状态中的场景指引。最新未缓存历史与状态作为 `contents` 继续发送。
- 请求通过 `cachedContent` 引用服务端缓存；已缓存的系统提示、工具和历史不重复发送。逻辑展开后的内容与同次完整请求一致。这里的稳定指“该缓存有效期间前缀不变”，并非永不变化。

### 生命周期与回退

- 第一版在成功生成后后台计数、创建或扩容，不让当前回复等待建缓存。首次或后台准备未完成时发送完整输入，不保证第二次请求就一定能引用显式缓存。
- 输入至少 4,096 tokens 才尝试准备；完整缓存是否满足当前模型最小长度，以创建 API 接受结果为准，失败退避。扩容先用长度粗筛，再以 `countTokens` 确认稳定历史比已有缓存至少增加 **2,048 tokens**；不是每隔固定轮数重建。检查间隔至少 30 秒，失败后退避 60 秒。
- TTL 10 分钟；到期前 30 秒不再新引用该缓存。系统提示、工具配置、历史压缩/改写、附件引用变化使已缓存前缀失配时，停止使用旧缓存，发送完整输入。
- 进程内按用户所属会话目录、模型、API 地址和凭据隔离缓存，不跨用户/会话共享。仅保存缓存引用和前缀哈希，不将正文、缓存 ID 或凭据写入缓存日志/持久缓存索引。最多保留 128 个会话配置项，空闲过期清理；替换、淘汰和正常关停时主动删除，删除失败由服务端 TTL 兜底。
- 缓存请求失败且尚未向调用方交付部分输出时，自动去掉缓存引用，用完整请求重试一次。取消请求不重试，已输出部分文本/工具事件后不重播。缓存准备失败不会阻断正常生成。
- `GEMINI_CONTEXT_CACHE_ENABLED=false` 可关闭显式缓存，Gemini 状态后置仍保留。Trace 新增 `model.cache` 的 `full_request`、`created`、`reuse`、`invalidate`、`fallback`、`prepare_failed` 事件；已有 usage 继续提供实际 cacheRead。

### 验证与线上观察

使用本机模拟 Google API 验证了真实 Pi/Google SDK 的缓存创建、缓存字段转换、Google Search + 函数工具循环、404 缓存回退；另覆盖状态不污染历史、账户/会话/凭据隔离、前缀/工具/记忆/附件变化、过期、后台准备、扩容、取消及避免重复播报。此处是实现验证，不是新增一轮真实 Google 命中率实验。

上线后应一起看 `model.cache` 和 `model.response`：先出现完整请求与后台 `created`，后续出现 `reuse`，再核对 cacheRead 的 token 数；`reuse` 表示引用缓存，不应单独充当供应商命中的证明。继续分别记录首次准备、稳定复用、刷新、回退及语音时延，新增结果仍追加在本文件后面。
